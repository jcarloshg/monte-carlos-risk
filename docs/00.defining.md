## 100. Planning Phase

### 1. Raw Business Vision & Workflows (Feeds Domain Discovery)

- **Q1.1 — Business model:** This is **not a commercial product**. It is a learning artifact that mirrors how quantitative trading firms evaluate strategies before deploying capital. The "paying user" is the author (a self-directed learner). Problem solved: turn a strategy idea into a probabilistic statement about expected loss (drawdown, tail risk) using Monte Carlo simulation on historical return distributions. No revenue, no SLA to customers.
- **Q1.2 — Core workflow:** Step-by-step happy path for this project:
  1. Author loads a portfolio of symbols (mock data) with historical daily returns.
  2. Author defines a simulation profile: number of paths, horizon, initial capital, confidence levels.
  3. System bootstraps / samples returns from the empirical distribution.
  4. System simulates N portfolio paths forward in time.
  5. System aggregates paths into a drawdown distribution and tail-risk metrics (VaR, CVaR).
  6. Author visualizes fan charts and histogram of terminal wealth / max drawdown via matplotlib.
  7. Author iterates on portfolio composition by re-running the simulation.

  Manual steps today: editing input JSON/CSV, re-running the container, reading the chart. There is no UI; the "user interface" is `docker compose up` plus reading generated PNGs.
- **Q1.3 — Domain glossary:** Ubiquitous-language candidates (the only ones that matter for this project's bounded context):
  - `Portfolio` — the set of holdings under simulation.
  - `Holding` / `Position` — a single symbol with a weight.
  - `Return` — a daily log/arith return observation.
  - `ReturnDistribution` — the empirical distribution of returns used for sampling.
  - `SimulationPath` — one Monte Carlo trajectory of portfolio value over the horizon.
  - `SimulationRun` / `MonteCarloRun` — the aggregate result of N paths.
  - `Drawdown` — peak-to-trough decline of a path.
  - `MaxDrawdown` — the worst drawdown observed across a path.
  - `ValueAtRisk (VaR)` — loss threshold at a confidence level (e.g., 95%).
  - `ConditionalVaR (CVaR)` — expected loss given loss ≥ VaR.
  - `TailRisk` — the right tail of the loss distribution.
  - `ConfidenceLevel` — e.g., 0.95, 0.99.
  - `Horizon` — number of trading days simulated per path.
  - `InitialCapital` — portfolio value at t=0.
  - `Seed` — RNG seed for reproducibility.

  Conflict / overlap notes: in a real quant shop, `Portfolio` in the OMS vs. `Portfolio` in the risk engine can mean different things. Here we have a single context, so no collision yet — but the DDD structure (see Q2.x in 200) must keep the risk-modeling concept of `Portfolio` decoupled from any future "execution" concept.
- **Q1.4 — Domain events:** Past-tense events that describe a simulation lifecycle:
  - `SimulationRequested` — author submits input config + seed.
  - `ReturnsLoaded` — historical return series attached to the run.
  - `PathSampled` — emitted per simulated path (or batched).
  - `DrawdownComputed` — per-path max drawdown derived.
  - `RiskMetricsCalculated` — VaR / CVaR aggregated from the path set.
  - `SimulationCompleted` — terminal state of the run.
  - `SimulationFailed` — emitted on invalid input or runtime error.

  These events exist to feed future projections (e.g., a dashboard or a downstream "compare strategies" service) — they are NOT delivered in v1 to a broker, an OMS, or any external system.
- **Q1.5 — Bounded context candidates:** For this project there is exactly **one bounded context** worth modeling: **Risk Simulation**. Natural future seams (called out only because the user wants the option to plug in third-party data later):
  - `MarketData` context (would own the historical return series — currently mocked).
  - `RiskSimulation` context (the core — owns Monte Carlo engine).
  - `Reporting` context (would own chart rendering and PDF/HTML output — currently just matplotlib PNGs).

  In v1 these collapse into one context with folder-level seams (`domain/`, `infrastructure/`, `interfaces/`) so the seams are explicit and swappable.
- **Q1.6 — Anti-anemic check:** Business rules that must always hold (encapsulated as invariants on aggregates, not as ad-hoc `if`s):
  - A `SimulationRun` cannot be started without a non-empty `Portfolio`.
  - Sum of `Holding` weights must equal 1.0 within `±1e-9` (or be explicitly declared as `leverage != 1`).
  - `Horizon` ∈ `[1, 10_000]` trading days.
  - `NumberOfPaths` ∈ `[100, 1_000_000]`.
  - `ConfidenceLevel` ∈ (0, 1).
  - `Seed`, if provided, must be a non-negative integer; if absent, the system records a generated seed for reproducibility.
  - A path's `MaxDrawdown` ∈ [0, 1] (cannot exceed 100% loss under long-only assumption; flagged if it does).
  - `VaR` and `CVaR` at confidence `c` must satisfy `CVaR ≥ VaR` (mathematical invariant — assert in tests).
- **Q1.7 — Existing PRD / docs:**
  - `README.md` (project-level brief) — read.
  - `PHASES-SUMMARY.md` (the wider 7-phase quant pipeline this project lives in, specifically **Phase 3: Backtesting & Simulation** + **Phase 5: Risk Management**) — read.
  - No PRD, no stakeholder interviews. Stakeholder is the author. No external stakeholder interviews are needed for an educational project.

  - `Portfolio`: `DRAFT → ACTIVE → ARCHIVED`. The author edits a JSON file to move between DRAFT and ACTIVE; ARCHIVED is implicit (file moved out).
- **Q5.5 — Forbidden transitions:**
  - `COMPLETED → RUNNING` (no resume).
  - `FAILED → COMPLETED` (no silent retry-success).
  - `ARCHIVED → ACTIVE` (archived portfolios cannot be silently reactivated).
- **Q5.6 — Error / empty / loading states:**
  - **Empty state** — no input file: CLI exits with non-zero code and a `PortfolioNotFoundError` message naming the expected path.
  - **Invalid config** — weight sum ≠ 1, out-of-range horizon: CLI exits with `ValidationError` and a line-numbered pointer to the offending field.
  - **Runtime failure** — numpy seed or out-of-memory: process exits non-zero, `FAILED` event persisted, exit message includes run-id and correlation-id (for log lookup).
  - **Loading state** — N/A (CLI is synchronous). For longer runs, a `tqdm` progress bar to stderr.
- **Q5.7 — Real-time needs:** None. No WebSocket, no streaming. Output is files-on-disk.

## 200. Design Phase

### 1. Finalized Domain Model (Feeds Bounded Contexts, Hexagonal Layers, CQRS Slices)

- **Q1.1 — Aggregates & roots:**
  - **`Portfolio`** is the root of the *Portfolio Definition* aggregate. Inside the consistency boundary: `Holding[]` (each with `symbol`, `weight`), `rebalancePolicy` (none in v1 — static weights).
  - **`SimulationRun`** is the root of the *Risk Simulation* aggregate. Inside the boundary: `Portfolio` (by id), `simulationProfile` (horizon, paths, confidence, seed), `paths[]` (or stored out-of-band), `riskMetrics` (VaR, CVaR, mean terminal wealth, std terminal wealth), `status`, `createdAt`, `completedAt`.
  - **`RiskMetrics`** is a value object inside the run aggregate (no separate identity).
- **Q1.2 — Entity identities:**
  - `Portfolio.id` — UUIDv4 (sufficient for a single-user system; UUIDv7 unnecessary here).
  - `Holding.symbol` — string, vendor-neutral (use mock tickers like `MOCK-AAPL`).
  - `SimulationRun.id` — UUIDv4.
  - `SimulationRun.seed` — `uint64` (numpy-compatible).
  - No natural keys; no auto-increment integers; no domain-meaningful numbers (no "RUN-000123").
- **Q1.3 — Domain events inventory:** (Re-stated, frozen for v1.)
  1. `SimulationRequested` — `{runId, portfolioId, profile}`.
  2. `ReturnsLoaded` — `{runId, observationCount, startDate, endDate}`.
  3. `PathSampled` — `{runId, pathIndex}` (batched per N=1000 paths in v1 to avoid log noise).
  4. `DrawdownComputed` — `{runId, pathCount}`.
  5. `RiskMetricsCalculated` — `{runId, var95, var99, cvar95, cvar99, meanTerminal, stdTerminal}`.
  6. `SimulationCompleted` — `{runId, durationMs}`.
  7. `SimulationFailed` — `{runId, reasonCode, message}`.

  Causal chain: `Requested → ReturnsLoaded → (PathSampled → DrawdownComputed)* → RiskMetricsCalculated → Completed`. Failure short-circuits the chain to `Failed`.
- **Q1.4 — Event granularity:** `PathSampled`, `DrawdownComputed` are emitted **once per batch** in v1, not once per path. Justification: emitting per-path is O(N) log lines, which adds no information at the granularity the human author cares about. If a downstream dashboard is ever added, it can subscribe to the batched event and the run-id carries the path set reference.
- **Q1.5 — Invariants:** Re-stated from Q1.6 above, plus aggregate-internal invariants:
  - A `SimulationRun` cannot transition `PENDING → RUNNING` without its `Portfolio` existing.
  - A `SimulationRun` cannot transition `RUNNING → COMPLETED` unless `riskMetrics` is set.
  - A `SimulationRun`'s `seed` is **immutable after creation** (preserves reproducibility).
  - A `Holding.weight` is a finite float, sum-bounded as above.
- **Q1.6 — Cross-context shared kernel:** Even in v1, two concepts must be shared because they have semantic meaning everywhere they appear:
  - `Money` / `Quantity` — represented as `Decimal` (not `float`) for any monetary aggregate; for v1, use plain `float` with a documented "educational precision is acceptable" note. Promote to `Decimal` if/when a real-money vendor is integrated.
  - `CorrelationId` — generated at the CLI entry point, propagated through logs and event payloads.
  - `DomainError` — a shared hierarchy (see 300-Q6.4).
  - `Clock` — injectable so tests can freeze time.
- **Q1.7 — Context map:** Single context for v1 (`RiskSimulation`). The DDD folder layout must make the future seams visible (`domain/portfolio`, `domain/simulation`, `domain/market_data` as sub-folders even when empty), and future vendor integrations land behind `Anti-Corruption Layer` adapters in `infrastructure/`.
- **Q1.8 — Long-running transactions:** None. A `SimulationRun` is the unit of work; no saga needed.
- **Q1.9 — Ubiquitous language glossary:** See Q1.3 above. The glossary lives in this file (and later, in a `docs/glossary.md` exported from this section). Naming in code MUST match (e.g., `SimulationRun`, not `MCJob`).

### 3. Definition of Ready & Story Slicing (Feeds TDD, Contract Tests, Stacked PRs)

- **Q3.1 — Definition of Ready sign-off:** Single-author repo, so **author = DoR gate**. A story is ready when its acceptance criteria are written (both happy and unhappy path) and its tests are sketched.
- **Q3.2 — Story size cap:** ≤ 1 day of work per story. Vertical slices only (e.g., "given CSV input, compute VaR" cuts through CSV adapter → domain → use case → CLI).
- **Q3.3 — Happy-path acceptance criteria:** Imperative Given/When/Then. Example:
  > Given a portfolio with weights `{AAPL: 0.6, MSFT: 0.4}` and 252 days of returns,
  > When I run `mc-risk run --portfolio p.json --paths 10000 --horizon 252 --seed 42`,
  > Then a PNG fan chart and a metrics JSON are written to `./output/<runId>/` and the process exits 0.
- **Q3.4 — Unhappy-path acceptance criteria:** Every story MUST enumerate at least:
  - Invalid portfolio (weight sum ≠ 1) → `ValidationError`, exit 2.
  - Missing CSV → `PortfolioNotFoundError`, exit 3.
