## 2. Design Activities Performed (Step 2)

### 2.1 Macro Architecture & Service Boundaries

#### 2.1.1 Modular monolith, single bounded context

Per ADR-001 (Planning), the v1 system is **one bounded context** (`RiskSimulation`)
inside a **single-process modular monolith**. No microservices, no containers
beyond the one Docker container that runs the CLI.

- **Service boundary = container boundary.** Everything runs in the same Python
  process. There is no network hop inside the system.
- **Domain seams are folder seams.** `src/domain/{portfolio,simulation,market_data,reporting,shared_kernel}`
  are sibling folders. `market_data/` and `reporting/` are reserved as future
  extraction boundaries per ADR-001.
- **No synchronous cross-service calls** — there are no services. All in-process
  calls are plain Python function calls.

#### 2.1.2 Asynchronous choreography vs. orchestration

Because there are no services, the choreography/orchestration dichotomy
collapses to **in-process event sequencing**:

- Events are emitted to a single writer (`JsonlEventWriter`, port
  `SimulationResultStore`).
- The "consumer" of an event is the next function in the engine pipeline
  (e.g., `PathSampled` → next batch loop → `DrawdownComputed`).
- **No orchestrator** (Step Functions / Temporal) is needed — the engine is a
  finite function with one entry point, not a long-running saga.
- **Future-proof:** if a `Reporting` context is ever extracted, the JSONL log
  becomes the choreography backbone (ADR-003 already documents this).

#### 2.1.3 Long-running transactions / sagas

**N/A — educational scope.** A `SimulationRun` is the unit of work and runs
synchronously inside one process (Defining Q5.4, ADR-001). No saga, no
compensation logic. The single-state-machine in
`docs/100.planning/diagrams/state-machine-simulation-run.md` covers all
transitions.

**Production fork note:** if `MarketData` is ever replaced by a real vendor
call, the `SimulationRun` could need a saga across "fetch returns" →
"simulate" → "persist metrics". The folder seam `src/domain/market_data/` and
the `MarketDataAcl` adapter (future) are the carve-out.

### 2.2 Micro Architecture & Codebase Design

#### 2.2.1 Hexagonal (Ports & Adapters)

Per ADR-002 (Planning), the layout is hexagonal. This phase **freezes the
Port inventory** (5 ports) and the **Adapter pairing rule** (each Port has ≥ 2
adapters at design time: 1 production, 1 in-memory/seeded).

Full port + adapter map: `architecture/hexagonal.md`.

| #   | Port (Protocol)         | Production adapter    | In-memory adapter          | Rationale                                               |
| --- | ----------------------- | --------------------- | -------------------------- | ------------------------------------------------------- |
| 1   | `ReturnRepository`      | `CsvReturnRepository` | `InMemoryReturnRepository` | Reads returns from disk vs. a `dict[date, list[float]]` |
| 2   | `SimulationResultStore` | `JsonlEventWriter`    | `InMemoryEventStore`       | Writes JSONL vs. `list[Envelope]`                       |
| 3   | `RNG`                   | `NumpyGenerator`      | `SeededGenerator(42)`      | Wraps `numpy.random.Generator` vs. a deterministic stub |
| 4   | `Clock`                 | `SystemClock`         | `FakeClock(frozen_at)`     | `datetime.now(tz=utc)` vs. a frozen `datetime`          |
| 5   | `Renderer`              | `MatplotlibRenderer`  | `NullRenderer`             | Writes PNGs vs. discards                                |

Each port has **two adapters at design time** — codified as a rule in
ADR-015 (this phase). If a port has only one implementation, the abstraction
is probably wrong; that is a code-review signal.

#### 2.2.2 CQRS scope

**N/A — educational scope.** No read/write asymmetry (Defining Q2.3: "N/A — no
read API") and no complex search views. The "read" is opening a PNG, which
bypasses the engine entirely.

Captured as ADR-011: "No CQRS in v1." If a `Reporting` context is ever
extracted, the projector pattern (events → denormalized read-store) is the
natural CQRS adoption point. Until then, adding a write-side / read-side
split would double the surface area for zero benefit.

**Production fork note:** if a REST `GET /runs` endpoint is ever added,
CQRS becomes justified. The natural projection target is a JSONL index file
per run (`./output/<runId>/index.jsonl`) keyed by `sequenceNumber`.

#### 2.2.3 Dependency injection

Per ADR-007 (Planning), DI is a **hand-rolled composition root** at
`src/interfaces/cli/main.py`. No `dependency-injector` / `inject` / `pinject`.

- A `Container` dataclass holds the wiring (one instance per CLI invocation).
- Use cases receive their ports via constructor parameters.
- Tests construct their own `Container` with in-memory adapters.

Captured as ADR-016: "Composition root as hand-rolled factory."

#### 2.2.4 Boundary linting

Per ADR-010 (Planning), the import-linter contract (`.importlinter`) is
**frozen** and runs as a blocking CI stage. The full contract:

```yaml
layers:
  - name: domain
    type: forbidden
    modules: [src.domain]
    forbidden:
      - src.infrastructure
      - src.interfaces
      - pandas
      - matplotlib
      - click
      - typer
      - docker
  - name: application
    type: forbidden
    modules: [src.application]
    forbidden: [src.infrastructure, src.interfaces]
  - name: shared_kernel
    type: independent
    modules: [src.domain.shared_kernel]
```

`mypy --strict` is the second half of the boundary gate (Protocol
conformance).

### 2.3 Data Architecture & Persistence Strategy

#### 2.3.1 Polyglot persistence

**N/A — educational scope.** The system has exactly one persistence need
(per-run JSONL event log + final metrics JSON), and one tool satisfies it
(stdlib `json` + `pathlib`).

Captured as ADR-012: "Single persistence choice (no polyglot)." The decision
matrix that would justify polyglot (e.g., PostgreSQL for ACID + Redis for
cache) reduces to a single column because the workload is single-process,
single-writer, single-reader (the CLI smoke test).

**Production fork note:** if a real-time `GET /runs` query surface is added,
a tiny read-store (SQLite or DuckDB) is the natural addition. The
`SimulationResultStore` port absorbs the change without touching the engine.

#### 2.3.2 CAP theorem — explicit stance

**N/A — educational scope.** There is no network, so the P (partition) leg
of CAP does not occur. The trade-off is therefore between two local
properties, not a distributed-systems one:

- **Within-process consistency:** every committed run is either `COMPLETED`
  with full `riskMetrics` OR `FAILED` with a `SimulationFailed` event.
- **Crash-durability:** JSONL is flushed per batch (ADR-009), so a crash
  loses at most one batch of compute. The `status.json` file is the source of
  truth for terminal state.

Captured as ADR-013: "CAP stance — N/A; single-process invariant." The
invariant (run is atomic: all-or-nothing) is enforced by the state machine in
`docs/100.planning/diagrams/state-machine-simulation-run.md`.

**Production fork note:** if `MarketData` becomes a remote vendor, the
implicit AP choice (run completes even if returns refresh mid-run) becomes a
real CAP negotiation with the author.

#### 2.3.3 One database per service

**Trivially satisfied.** One context = one store (`./output/<runId>/`). No
cross-service access exists because there is only one service.

The future-extraction rule (when `MarketData` or `Reporting` becomes a
sibling context): each new context gets its own directory under
`./output/<contextName>/<aggregateId>/` and reads from other contexts'
stores **only** via their published events (choreography) or public APIs.

#### 2.3.4 Transactional Outbox

**N/A — educational scope.** The outbox pattern exists to make
"save-to-DB-then-publish-to-broker" atomic. We have no broker and no DB — we
have one file and one writer process.

The equivalent guarantee is achieved differently:

- **`SimulationResultStore` writes are sequential and flush-per-batch.**
  The in-process engine cannot interleave a "save metrics.json" with a
  "write event" because it is one thread.
- **Crash recovery:** on startup, `ReplaySimulation` reads
  `./output/<runId>/status.json`. If `RUNNING`, the run is corrupt; the user
  re-runs. If `COMPLETED` or `FAILED`, the run is terminal.

Captured as ADR-014: "No transactional outbox in v1; in-process sequential
writes + per-batch flush are sufficient."

**Production fork note:** the day a Kafka broker is added, the outbox
pattern becomes mandatory. The migration is: introduce a `PendingEvent` table
in the broker adapter; the engine writes to the JSONL AND to the
`PendingEvent` table in the same logical step; a background worker polls
`PendingEvent` and publishes to Kafka, marking the row as published.

#### 2.4.2 ERD (datastore entity-relationship)

- `SimulationRun` (the aggregate root, recorded in `status.json`).
- `Envelope` (every JSONL row) — 1-to-many per run.

declarative of the JSON shape; the C4-container diagram is declarative of
the runtime topology.

## 3. Anti-Pattern Self-Check (Step 3 of playbook)

Each anti-pattern from the playbook is explicitly considered and rejected
**with reason** (or accepted with a documented override).

| #   | Anti-pattern                                     | Decision   | Reason                                                                                                                                                     |
| --- | ------------------------------------------------ | ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **The Distributed Monolith**                     | ❌ Rejected | There are no distributed services. Single process, single binary. Future extraction is bounded by ADR-001 folder seams.                                    |
| 2   | **Database-Driven Design**                       | ❌ Rejected | No ORM. Persistence is an adapter behind `SimulationResultStore`. Domain entities (Pydantic models) are pure data classes; the adapter maps JSON ↔ domain. |
| 3   | **The God Database**                             | ❌ Rejected | There is exactly one persistence directory (`./output/`). Future contexts get sibling directories; no shared store.                                        |
| 4   | **The Ivory Tower Wiki**                         | ❌ Rejected | Diagrams are structural (C4 L1+L2, state machines, ERD). Detail lives in code + ADRs, not in 40-page wiki pages.                                           |
| 5   | **The "Build It and They Will Come" Assumption** | ❌ Rejected | NFRs in `docs/100.planning/01.planning.md` §2.2 are quantified (paths/sec, P95 wall-clock, memory budget). Every infra choice ties to a number.            |
| 6   | **Anemic Domain Model**                          | ❌ Rejected | Aggregates own invariants (Defining Q1.6). `SimulationRun.run()` carries the lifecycle; no service-layer `if`s.                                            |
| 7   | **Gold-Plating Scalability**                     | ❌ Rejected | No Kafka, no Postgres, no Redis. Stack is `uv` + `numpy` + `pydantic` + `structlog` + `matplotlib` + `click`.                                              |
| 8   | **Resume-Driven Development**                    | ❌ Rejected | No Kubernetes, no Helm, no Terraform, no service mesh. `docker compose up` is the deployment story (ADR-007).                                              |

## Quick-Reference Summary

Skim-readable condensation of this phase. For detail, follow the section anchors
above.

### Mission

Translate the frozen Planning artifacts (1 bounded context, 7 events, 10
Planning ADRs) into the **Architectural Blueprint** the Coding phase will
build against: a single-process modular monolith with a hexagonal layout,
exactly one persistence surface (JSONL), five Ports each with two Adapters,
and an explicit list of production patterns we are *not* adopting (CQRS,
polyglot persistence, transactional outbox, DI library) with the reason.
Scaled to a one-author, $0-budget, single-process learning repo; every
section below is sized to that reality.

### Key Decisions

- **ADR-011** no CQRS in v1 — no read API exists; adding a write/read split
  would double surface area for zero benefit. Trigger for future adoption: a
  `Reporting` context with a query endpoint.
- **ADR-012** single persistence choice — stdlib JSONL is sufficient;
  polyglot persistence is rejected because the workload is one-writer-one-reader.
- **ADR-013** CAP stance — N/A (single-process); local "all-or-nothing"
  invariant on `SimulationRun` is the equivalent.
- **ADR-014** no transactional outbox in v1 — single writer + per-batch flush
  achieve the equivalent guarantee. Migration plan documented for future Kafka.
- **ADR-015** port inventory & swappability — 5 ports frozen; each has ≥ 2
  adapters at design time (1 production + 1 in-memory/seeded).
- **ADR-016** hand-rolled composition root — no DI library; `Container`
  dataclass at `src/interfaces/cli/main.py`.
- **Inherited:** ADR-001 (single context), ADR-002 (hexagonal layout),
  ADR-003 (JSONL store), ADR-004 (Pydantic codegen), ADR-005 (CLI-only),
  ADR-006 (seeded RNG), ADR-007 (Docker compose), ADR-008 (structlog),
  ADR-009 (batched events), ADR-010 (CI gate).
- **Rejected:** distributed monolith, database-driven design, god database,
  ivory-tower wiki, build-it-and-they-will-come, anemic domain,
  gold-plating scalability, resume-driven stack (see §3).
