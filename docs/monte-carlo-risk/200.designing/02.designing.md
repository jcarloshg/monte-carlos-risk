## 1. Macro Architecture & Service Boundaries

### Decision: Modular Monolith (single Python process)

The macro architecture is a **modular monolith**: one Python process, one Docker image, four bounded contexts (`Portfolio`, `Simulation`, `RiskMetrics`, `Visualization`) as in-process modules. There is no inter-process communication, no service mesh, no message broker.

This is **not** a "monolith because we couldn't be bothered to split it" — it is the deliberate answer to *"would splitting these four contexts into separate processes pay for its own ops cost?"* The answer is no, and ADR-006 documents the justification.

**Service-boundary naming** uses the Ubiquitous Language from Planning §1 verbatim: `Portfolio`, `Simulation`, `RiskMetrics`, `Visualization`. No technical-layer names (`Service`, `Manager`, `Engine`) leak into the vocabulary.

### Async Choreography vs Saga

The playbook says: *"For cross-service workflows, prefer event-driven … When the distributed transaction has many steps, long runtime, or rollback requirements, use a Saga with Orchestrator."*

This project has no cross-service workflows (no services). The in-process orchestration of `Portfolio → Simulation → RiskMetrics → Visualization` is implemented as a **synchronous orchestrator** (`RunSimulation` use case in `application/`) that emits domain events with a `run_id` envelope. The event schemas in `contracts/events.schema.json` define the contract that the orchestrator enforces. ADR-006 §Consequences records this as the v1 answer; a future migration to a true event bus would require re-running this Design skill.

### Diagram: at-process level

Already captured in `100.planning/diagrams/c4-container.md`. The Design phase **adopts that diagram unchanged** because it already reaches container-level detail appropriate for a single-process system. The C4 stop-at-container rule from the playbook is honored: no component-level UML is added.

## 2. Micro Architecture & Codebase Design

### Hexagonal (Ports & Adapters)

Already adopted in Planning ADR-001. This Design phase adds the **concrete package layout**, **port module shape**, and **import-linter contract file** that the 300 (Coding) phase will implement. Full detail: `architecture/hexagonal.md` and `adr/007-hexagonal-package-layout.md`.

**Summary of the concrete shape:**

```
src/monte_carlo_risk/
  domain/
    portfolio/      # Portfolio, Holding, Ticker, Weight value objects
    simulation/     # SimulationRun, PathSet, Path (numpy-backed)
    risk_metrics/   # RiskReport, VaR, CVaR
    visualization/  # ChartArtifact (chart contract, NOT rendering)
  application/
    use_cases/
      run_simulation.py           # the orchestrator
      validate_portfolio.py
      describe_mock_data.py
    ports/
      market_data_source.py       # MarketDataSource Protocol
      chart_renderer.py           # ChartRenderer Protocol
      rng.py                      # DeterministicRNG Protocol
  infrastructure/
    market_data/
      mock_market_data_source.py
      http_market_data_source.py  # v2 stub
    rng/
      numpy_rng.py                # DeterministicRNG impl
    rendering/
      matplotlib_renderer.py
    filesystem/
      csv_return_matrix_loader.py
  interface/
    cli/
      app.py                      # Typer root
      commands/
        simulate.py
        validate_portfolio.py
        describe_mock_data.py
    errors.py                     # canonical JSON error envelope
    logging.py                    # structlog setup
```

The domain layer **never** imports from `application/`, `infrastructure/`, `interface/`. The `import-linter` contract file (`.importlinter`) enforces this in CI; details in `architecture/hexagonal.md` §Linter Contract.

### Dependency Injection

Aggressive DI is **not** needed at the scale of one process + one developer. Instead, each use case in `application/use_cases/` accepts its dependencies as **constructor arguments** with Protocol types; a thin composition root in `interface/cli/app.py` wires the concrete adapters at startup. Tests construct use cases with fake adapters directly. No DI container (Awilix, etc.) is introduced — it would be over-engineering for a single binary.

### CQRS

**Not adopted.** Decision documented in `adr/008-no-cqrs.md`. There is no read/write asymmetry: the CLI reads nothing across runs (ADR-004 / `adr/009-zero-datastores.md`), and within a run there is exactly one read (the chart output) of the just-written `RiskReport`.

### Layer-Boundary Enforcement

The `import-linter` config (`architecture/hexagonal.md` §Linter Contract) is the **automated guard**. Code review is a backstop, not the primary mechanism. The CI job (`hexagonal-purity`) runs `lint-imports` and fails the build on any forbidden import. The Python `mypy --strict` job catches Protocol drift before runtime.

## 3. Data Architecture & Persistence Strategy

### Polyglot Persistence

**Decision: zero datastores.** Documented in `adr/009-zero-datastores.md`. There is no SQL DB, no document store, no cache, no queue, no Parquet files, no `data/*.db`. The "store" is the filesystem (only via `infrastructure/filesystem/`), and even that is read-only at runtime for the bundled mock corpus.

The `db-erd.md` artifact captures this explicitly: see `diagrams/db-erd.md`.

### CAP Trade-Off

**Decision: AP for every context.** Documented in `adr/010-cap-ap.md`. There is no replication, no consensus, and no network partition in a single-process system. "Consistency" collapses to **single-process in-memory determinism** (NFR-4): the same inputs produce the same outputs. This is a **stronger** consistency guarantee than CAP's "strong consistency" (because there is no distributed state to disagree about), but the CAP trade-off is moot because there is no P in v1.

The business decision recorded here: if v2 ever introduces a real distributed store or message broker, the project MUST re-open this ADR and choose AP vs CP per context. The default going in would be AP (continue to favor availability), but the choice must be re-negotiated with stakeholders at that point.

### Transactional Outbox

**Decision: not applicable.** Documented in `adr/011-no-transactional-outbox.md`. There is no message broker, so there are no dual-writes to worry about. The in-process event emission is **synchronous and atomic** with the use case that produces it; there is no opportunity for a partial-write inconsistency. If v2 introduces a broker, this ADR must be re-opened and a transactional-outbox pattern added.

### One Database per Service

N/A — there are no services and no databases. The principle is recorded in `adr/009-zero-datastores.md` §Consequences so future contributors don't introduce a shared filesystem-backed "database."

## Quick-Reference Summary

### Mission
Translate the frozen Planning artifacts into the concrete package layout, port surfaces, sequence diagrams, and design-phase ADRs that the 300 (Coding) phase can implement without re-deciding anything architectural. Lock down the hexagonal tree, the deterministic RNG strategy, and the explicit "no" answers (no microservices, no DB, no broker, no CQRS, no outbox) so v2 work requires re-running Design rather than silently introducing them.

### Key Decisions
- **ADR-006** — Modular monolith (single Python process). Microservices explicitly rejected — no ops cost justified by NFR-1 / NFR-8.
- **ADR-007** — Hexagonal package layout frozen: `domain/{portfolio,simulation,risk_metrics,visualization}` + `application/{use_cases,ports}` + `infrastructure/{market_data,rng,rendering,filesystem}` + `interface/cli`. `import-linter` + `mypy --strict` enforce.
- **ADR-008** — No CQRS. No read/write asymmetry, no read store.
- **ADR-009** — Zero datastores. No SQL, no document store, no cache. Reproducibility derives from `(seed, portfolio, n_paths, horizon)`.
- **ADR-010** — AP for all four contexts. Single-process in-memory determinism is stronger than CAP "strong consistency" but the CAP trade-off is moot (no P in v1).
- **ADR-011** — No transactional outbox. No broker, no dual-writes.
- **ADR-012** — `numpy.random.default_rng(seed)` (PCG-64) wrapped in `DeterministicRNG` Protocol in `infrastructure/rng/`.
- **Anti-patterns rejected:** distributed monolith, database-driven design, god DB, ivory-tower wiki, "build it and they will come."
