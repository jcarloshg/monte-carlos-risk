## 1. 100 — Planning (The Business Reality)

### Domain & Flow

- **What the business sells.** An educational, locally-runnable Python tool that simulates thousands of possible portfolio paths using historical return distributions and reports drawdown probabilities and tail risk. It is a teaching artifact, not a product.
- **Happy path (first touch → revenue).** There is no revenue. The user journey is:
  1. `git clone` the repo → `docker compose up` → CLI ready.
  2. User defines a portfolio (tickers + weights) via CLI flags or config file.
  3. CLI loads bundled mock return data via the `MarketDataSource` port.
  4. Simulation engine runs N paths (default 10,000) over horizon H (default 252 trading days).
  5. `RiskMetrics` context computes max drawdown distribution, VaR, CVaR, terminal wealth distribution.
  6. `Visualization` context emits PNG charts + a JSON summary report to stdout / output dir.
  7. User inspects results locally.
- **Core domain events (past tense).**
  - `PortfolioDefined`
  - `MarketDataLoaded`
  - `SimulationStarted`
  - `SimulationCompleted`
  - `RiskMetricsCalculated`
  - `ChartsRendered`

### Targets & Budget

- **DAU / MAU.** N/A — single-user educational tool. Treat as 1 user.
- **Peak TPS.** < 1 (one CLI run at a time). The compute-bound unit is Monte Carlo path generation, not request handling.
- **P50 / P95 / P99 latency.** Wall-clock target for one default run (10,000 paths × 252 days, ~30-asset portfolio): P50 ≤ 10 s, P95 ≤ 30 s on a modern laptop. Asserted as a pytest-benchmark gate, not an SLA.
- **Monthly cloud ceiling.** **$0.** Runs locally in Docker; no cloud spend.
- **Team size & on-call tolerance.** 1 developer (jcarloshg). No on-call rotation. Single point of failure accepted.

### Resilience & Compliance

- **Uptime SLA.** None — local CLI. "Availability" = does `docker compose up` work on a clean machine.
- **CAP stance per context.** All four contexts are **AP** (best-effort, partition-tolerant) by default — there is no replication and no consensus to maintain. **CP is not relevant** because there is no network partition to tolerate; the "consistency" property collapses to "single-process in-memory state."
- **RPO / RTO.** N/A — no persistence, nothing to recover. A failed run is simply re-run.
- **Regulatory scope.** **None.** No PCI, GDPR, HIPAA, or SOC 2 obligations. No real customer data, no real market positions, no real money. Mock data only.

### Dependencies

- **3rd-party vendors.** Today: none (mock data only). Future: a real market-data API for the `MarketDataSource` port — candidates are **Yahoo Finance** (free, unofficial), **Alpha Vantage** (free tier with rate limits), or **Polygon.io** (paid). Vendor is **undecided** at this stage; the port is designed generically.
- **Legacy systems.** None.
- **Sandbox availability.** N/A — no vendor is integrated yet.
- **Rate limits.** N/A today. Will become relevant when the real API is wired in (e.g., Alpha Vantage free tier = 5 req/min, 500 req/day). To be re-evaluated at integration time.
- **Spikes / PoCs needed before commit.** A 1-day **timeboxed Spike** is required before wiring the real `MarketDataSource`:
  - Pick vendor (Yahoo vs Alpha Vantage vs Polygon).
  - Confirm return-series shape (daily log returns vs simple returns, adjusted vs unadjusted).
  - Confirm rate limits and licensing terms for educational use.
  - Output: a short ADR in `100.planning/`.

## 2. 200 — Design (The Architecture)

### Bounded Contexts

Four contexts, each owning its own aggregate roots, invariants, and ubiquitous language. Seams are enforced by hexagonal architecture + CI import lint.

| Context           | Aggregate Root                                      | Core Invariants                                                                               | Owns Events                                |
| ----------------- | --------------------------------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------ |
| **Portfolio**     | `Portfolio` (collection of `Holding` value objects) | Weights sum to 1.0; no negative weights; ticker set is non-empty.                             | `PortfolioDefined`                         |
| **Simulation**    | `SimulationRun` (parameters + generated paths)      | `n_paths > 0`; `horizon > 0`; RNG seed reproducibility (deterministic for same seed).         | `SimulationStarted`, `SimulationCompleted` |
| **RiskMetrics**   | `RiskReport` (computed statistics)                  | VaR / CVaR computed at declared confidence level; drawdown computed per-path then aggregated. | `RiskMetricsCalculated`                    |
| **Visualization** | `ChartArtifact` (PNG + JSON metadata)               | One chart per metric; file paths are stable and idempotent for same inputs.                   | `ChartsRendered`                           |

**Ubiquitous language glossary (locked):**
- *Portfolio* — set of holdings with weights summing to 1.0.
- *Path* — one simulated trajectory of cumulative portfolio value across the horizon.
- *Drawdown* — peak-to-trough decline along a single path.
- *VaR* — Value-at-Risk at confidence α (e.g., 95%) over the horizon.
- *CVaR* — Expected Shortfall, the mean loss conditional on loss exceeding VaR.
- *Mock return* — a synthetic daily log return sampled from a calibrated distribution; not real market data.

**Seams between contexts:** all communication is one-way through the application layer (`Simulation` consumes `Portfolio`; `RiskMetrics` consumes `Simulation`; `Visualization` consumes `RiskMetrics`). Contexts never import each other's internals — only shared kernel value objects (`Ticker`, `Weight`, `Return`, `Currency`).

### Data Strategy

- **Read / write ratio.** Pure read at runtime — mock data is loaded once per run. No transactional writes.
- **Polyglot persistence.** **None.** Pure in-memory. Each CLI run is a fresh process; no DB, no cache, no queue.
- **Hot / cold retention.** N/A.
- **Archival policy.** Optional: a user-configurable `output_dir` may receive PNG + JSON artifacts per run. Files are overwritten on each run with the same seed; nothing is retained across runs unless the user copies them out.

### Failure Tolerances

- **DLQ policy.** N/A — no message broker.
- **Saga vs choreography.** N/A — no distributed transactions; the pipeline is a single synchronous CLI invocation orchestrated by the application layer.
- **Circuit-breaker strategy.** Will become relevant when the real `MarketDataSource` API is wired in (open after N consecutive failures, half-open after cooldown). For mock source: not applicable.
- **Idempotency & out-of-order handling.** CLI runs are inherently idempotent given the same `(seed, portfolio, n_paths, horizon, mock_data_version)` tuple. Out-of-order handling N/A (no event stream).

### Contracts

- **OpenAPI / AsyncAPI / GraphQL.** **None required.** There is no public service surface; the tool exposes a CLI. The CLI's argument schema is the contract and is documented in `--help` plus a `docs/cli.md` page.
- **Internal port contracts.** The `MarketDataSource` Protocol is the most important contract and **must** be drafted as a Python Protocol (PEP 544) with at least two reference implementations: `MockMarketDataSource` (bundled CSVs) and `HttpMarketDataSource` (future). This Protocol is the seam that lets a real API be swapped in later.
- **Mock server / parallel frontend.** N/A — no frontend, no service boundary to mock.

## 3. 300 — Coding (The Execution Baseline)

### Sprint Zero & Tooling

- **CI/CD pipeline.** GitHub Actions: lint (ruff + import-linter) → unit tests (pytest) → domain-purity job (forbid infrastructure imports in `domain/`) → build Docker image → smoke test the image runs `monte-carlo --help` successfully.
- **Local dev environment.** Docker + docker compose (`docker compose up` brings up a dev container with the project mounted). Single command bootstrap: `make bootstrap` (or `just bootstrap`) runs `pip install -e .[dev]` + `pre-commit install`.
- **Boundary linting.** `import-linter` (or `dependency-cruiser` equivalent for Python) configured with rules:
  - `domain` must not import from `infrastructure`, `application`, or `interface`.
  - `application` may import from `domain` only.
  - `infrastructure` may import from `domain` and `application`.
  - `interface` (CLI entrypoints) may import from all layers.
- **One-command bootstrap.** `git clone … && make bootstrap && make test` lands on a green pipeline on a clean machine.

### Layer Enforcement

- **Hexagonal / DDD layout** (canonical):
  ```
  src/monte_carlo_risk/
    domain/              # pure: Portfolio, Simulation, RiskMetrics, Visualization aggregates + value objects
    application/         # use cases that orchestrate contexts
    infrastructure/      # MarketDataSource adapters (Mock, future Http), RNG, file I/O
    interface/           # CLI entrypoint (Typer / Click)
  tests/
    unit/                # fast domain tests, no I/O
    integration/         # Testcontainer-style tests for infra adapters against real files
    e2e/                 # CLI smoke tests via the Docker image
  ```
- **Domain purity CI job.** A dedicated GitHub Actions step that runs `import-linter` and fails the build if any `domain/**` module imports `numpy` for I/O, `pathlib`, `requests`, `typer`, or any third-party I/O library. (`numpy` is permitted inside `domain` for the math itself — it is a domain primitive, not infrastructure.)
- **tsconfig equivalent.** Python has no path restrictions by default; we rely on `import-linter` + `ruff` for the equivalent guardrails.

### Story Slicing

- **Vertical slice rule.** Every ticket must touch DB-adapter-or-mock → domain → application → interface in one PR, even when only one layer changes. No horizontal-only PRs.
- **Size cap.** ≤ 3 story points; anything larger is re-split before sprint planning.
- **Acceptance criteria.** Both happy and unhappy paths declared in the ticket body **before** sprint planning. Examples:
  - Happy: "Given a 3-asset portfolio with weights summing to 1.0, when I run `monte-carlo simulate --paths 10000`, then a PNG of the path distribution is written to `./output/paths.png` and a JSON report is printed to stdout."
  - Unhappy: "Given weights summing to 0.95, when I run `monte-carlo simulate`, then the CLI exits non-zero with code 2 and prints a structured error `weights_sum_must_equal_one`."

### Observability

- **Structured logging.** `structlog` emitting JSON to stderr. Levels: `DEBUG`, `INFO`, `WARNING`, `ERROR`.
- **Correlation ID.** A `run_id` (UUID4) is generated at CLI startup, logged on every event, and embedded in every output artifact filename (`output/{run_id}_paths.png`).
- **Tracing.** OpenTelemetry is **out of scope** for v1 — a CLI tool has no distributed trace. Re-evaluate if/when the project gains an HTTP service surface.
- **Centralized error middleware.** A single CLI-level error handler converts domain exceptions into a canonical JSON error schema printed to stderr:
  ```json
  {"error_code": "weights_sum_must_equal_one", "message": "...", "context": {...}, "run_id": "..."}
  ```

## 4. 400 — Testing (The Quality Gates)

### Modern Test Pyramid

- **Floor — fast domain unit tests.** `pytest` unit tests per aggregate, per value object, per use case. Target: full suite < 5 s. No I/O in this layer.
- **Middle — Testcontainer-style integration tests** for `infrastructure/` adapters. The mock CSV loader is exercised against real files in a tmp dir. Future `HttpMarketDataSource` will be tested against a `responses` / `vcr.py` cassette — or a real Testcontainer if the vendor offers one. No live network calls in CI.
- **Top — minimal E2E.** Build the Docker image, run `docker run … monte-carlo simulate --portfolio …`, assert PNG + JSON exit 0. **Budget: ≤ 20 minutes** total for the E2E suite. Today this is one job; if it grows beyond 20 min, the surplus moves to integration tests.

### Contract Testing

- **Consumer-Driven Contracts (Pact).** N/A — there is no producer/consumer service boundary in v1. The internal `MarketDataSource` Protocol is verified via two reference implementations (`MockMarketDataSource`, `HttpMarketDataSource`) sharing a contract test suite.
- **Shared staging environment.** **Banned.** No staging environment. Local + CI is sufficient.

### Performance

- **Load / stress tests.** `pytest-benchmark` asserts the wall-clock targets from the 100 phase (P50 ≤ 10 s, P95 ≤ 30 s for default run) as a build-breaking threshold. Beyond the default benchmark, **no sustained-load tests** — a single CLI run is the entire workload.
- **Chaos tests.** Out of scope for v1. Re-introduce if a real network call becomes part of the hot path.

### Shift-Right (Prod)

- **Feature flags.** Not applicable — there is no production environment. The closest analog is a `--provider mock|http` flag on the CLI; defaulting to `mock`.
- **Canary deployments.** N/A.
- **Synthetic monitors.** N/A.
- **Prod-as-test-environment.** N/A. The local Docker run is the final acceptance gate.

## Quick-Reference Summary

### Project Snapshot
Educational Python tool that runs Monte Carlo simulations of portfolio paths against mock historical return distributions, then reports drawdown probabilities and tail risk (VaR, CVaR). Built with numpy and matplotlib, packaged as a single Docker image, run via a CLI. Sole user is the developer; the explicit goal is to demonstrate strict hexagonal DDD so a real market-data API (Yahoo Finance / Alpha Vantage / Polygon) can be swapped in later via a `MarketDataSource` port without touching the domain.

### Key Targets
- Monthly infra budget: **$0** (local Docker only).
- Wall-clock per default run (10k paths × 252 days × ~30 assets): **P50 ≤ 10 s, P95 ≤ 30 s** on a modern laptop; asserted as a CI benchmark gate.
- Availability SLA: **none** (local CLI; "available" = `docker compose up` works on a clean machine).
- CAP stance: **AP** for every context (single process, no replication, no partition tolerance to negotiate).
- Regulatory scope: **none** (no real money, no real customer data, mock data only).

### Bounded Contexts
- **Portfolio** → `PortfolioDefined`
- **Simulation** → `SimulationStarted`, `SimulationCompleted`
- **RiskMetrics** → `RiskMetricsCalculated`
- **Visualization** → `ChartsRendered`

### Critical Constraints
- Strict hexagonal architecture with `import-linter` enforcing `domain/` purity (no I/O, no HTTP, no CLI imports in domain).
